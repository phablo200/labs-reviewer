# MongoDB Integration

## Objective

Add a MongoDB-backed process status design for the Labs workflow, documented before implementation. The goal is to prepare persistence, services, repositories, configuration, and routing foundations for tracking each uploaded Markdown processing job, including parent agents, child/sub-agent execution, final agent results, and the processed file name.

This spec is planning-only. No runtime code should be implemented until the implementation step is explicitly requested. This spec does not implement agent workflow status updates; a follow-up spec will define how agents write process and result data.

## Background

The current backend accepts Markdown files through `POST /labs/review`, schedules processing in a FastAPI background task, and writes generated Markdown/PDF output files under `public/markdown/` and `public/pdf/`.

The workflow uses multiple agents:

- Labs Writer
- Labs Reviewer
- Labs Code Examples
- Labs Metadata
- Labs Translator

Some agents run independently, while others behave as child steps inside a parent workflow. The most important example is the reviewer flow, where Labs Reviewer may run multiple review loops for Labs Writer. The frontend needs a status endpoint that can show both the top-level process status and nested agent/sub-agent progress.

The architecture note in `.workspace/mongodb-integration.md` recommends MongoDB for this feature because the status shape is document-oriented and naturally stores nested agent state. It also recommends Beanie with PyMongo Async instead of Motor directly, because this project is FastAPI + Pydantic v2 and Motor is being deprecated.

## Scope

In scope:

- Document the MongoDB integration plan in `docs/specs/mongodb-integration.md`.
- Plan the migration of the existing Labs orchestration files into `labs/agents`.
- Define the new `labs/process_status` package.
- Define the `process_status` MongoDB document structure.
- Include `result` on each `AgentStatus`.
- Include `file` on `ProcessStatus`.
- Keep process and nested agent state in one MongoDB document for the first implementation.
- Prepare the status endpoint at `GET /labs/processes/{process_id}/status`.
- Store agent `result` values in MongoDB, but exclude `result` from the status endpoint response.

Out of scope for this spec:

- Implementing code changes.
- Installing Beanie or PyMongo dependencies.
- Adding MongoDB startup/shutdown lifecycle code.
- Refactoring the background task workflow.
- Updating existing agents to create or mutate process status.
- Defining the future agent-result endpoint that returns `AgentStatus.result`.
- Adding tests.

The new MongoDB process status module should live separately from the agent implementation:

```text
labs/
  process_status/
    __init__.py
    models.py
    repository.py
    service.py
    router.py
```

Recommended responsibilities:

- `labs/process_status/models.py`: Beanie document and embedded Pydantic models.
- `labs/process_status/repository.py`: direct persistence operations.
- `labs/process_status/service.py`: process-status business operations.
- `labs/process_status/router.py`: HTTP status endpoint at `GET /labs/processes/{process_id}/status`.

MongoDB app lifecycle should be handled outside this package, likely under `core/database/mongodb.py`, when implementation begins.

## Data Model

Use one MongoDB document collection named `process_status`.

### AgentStatus

Each top-level agent and child/sub-agent should be represented by `AgentStatus`. The `result` field stores the output/result generated by that agent when available.

```python
class AgentStatus(BaseModel):
      id: UUID
      name: str
      status: Literal["IN_PROGRESS", "FAILED", "SUCCEEDED"]
      loop_from: int | None = None
      loop_to: int | None = None
      finished_at: datetime | None = None
      result: str | None = None
      children: list["AgentStatus"] = []
```

Implementation note: when this is implemented with Pydantic, prefer `Field(default_factory=list)` for `children` to avoid shared mutable defaults.

The `result` field is persisted for future result retrieval, but it must not be returned by `GET /labs/processes/{process_id}/status`. A later spec will define an agent-process endpoint that retrieves the stored result for a specific agent process.

### ProcessStatus

Each uploaded file processing job should create one `ProcessStatus` document. The `file` property stores the processed file name.

```python
class ProcessStatus(Document):
      id: UUID
      file: str
      created_at: datetime
      user_id: UUID
      data: list[AgentStatus]

      class Settings:
          name = "process_status"
```

Implementation note: use UUID and datetime default factories during implementation so callers do not have to manually populate every field.

## Status Endpoint

Use this endpoint for process status reads:

```text
GET /labs/processes/{process_id}/status
```

The endpoint should return status metadata only. It should include process fields, agent names, statuses, loop metadata, finish timestamps, and nested children. It should not include `result`, even though `result` is stored in MongoDB.

## Implementation Plan

1. Migrate files:
   Move `labs/contants.py`, `labs/router.py`, and `labs/service.py` into `labs/agents/`.

2. Update imports:
   Update `main.py`, tests, helpers, and any internal imports that reference the old module paths.

3. Create process status package:
   Add `labs/process_status` with `models.py`, `repository.py`, `service.py`, and `router.py`.

4. Add MongoDB dependencies:
   Add Beanie and PyMongo Async-compatible dependencies to `requirements.txt`.

5. Add MongoDB configuration:
   Add `MONGODB_URI` and `MONGODB_DATABASE` to `core/config.py` and `.env.example`.

6. Add MongoDB lifecycle:
   Initialize and close MongoDB from FastAPI lifespan in `main.py`.

7. Prepare status response schemas:
   Add response models or serialization helpers that remove `result` from the `GET /labs/processes/{process_id}/status` payload while keeping it in the persisted document.

8. Add status endpoint:
   Expose `GET /labs/processes/{process_id}/status` as a protected endpoint that reads process status by process id and authenticated user id.

9. Stop before agent workflow integration:
   Do not update existing agents, background tasks, or Markdown/PDF workflow behavior in this spec. A follow-up spec will define when process records are created, how statuses transition, and how agent results are retrieved.

## Acceptance Criteria

- The implementation spec exists at `docs/specs/mongodb-integration.md`.
- Existing Labs API/orchestration modules are planned to move under `labs/agents`.
- The MongoDB process status package is planned under `labs/process_status`.
- `AgentStatus` includes `result: str | None = None`.
- `ProcessStatus` includes `file: str`.
- The collection name is `process_status`.
- The status data model supports nested child agents.
- The status endpoint path is `GET /labs/processes/{process_id}/status`.
- The status endpoint response excludes `result`.
- Existing agent workflow behavior is not changed by this configuration-focused implementation.
- The plan keeps implementation work separate from this specification step.

## Test Plan

When implementation is requested, add or update tests for:

- Import path migration from `labs.*` to `labs.agents.*`.
- `AgentStatus` default values and nested child serialization.
- `ProcessStatus` collection name and required fields.
- Repository create/read/update behavior with Beanie test isolation.
- Protected `GET /labs/processes/{process_id}/status` endpoint authorization.
- Status endpoint returns only processes owned by the authenticated user.
- Status endpoint serialization excludes every `result` field, including nested child-agent results.
- Repository/service methods can persist and read `result` internally without exposing it through the status endpoint.

## Risks And Mitigations

- Async database writes from the current synchronous background helper may complicate implementation.
  Mitigation: keep Markdown/PDF helpers focused on file work and move orchestration/status updates into an async workflow/service layer.

- Storing large agent results directly in the process document could make documents too large over time.
  Mitigation: store concise results initially; move large artifacts to output files or a separate collection if needed.

- Moving `labs/router.py` and `labs/service.py` may break imports across tests and docs.
  Mitigation: migrate imports in one pass and run focused tests after the move.

- Mutable defaults in nested Pydantic models can cause shared list state.
  Mitigation: use `Field(default_factory=list)` during implementation.

## Resolved Decisions

- The status endpoint path is `GET /labs/processes/{process_id}/status`.
- `AgentStatus.result` is persisted but not returned by the status endpoint.
- A follow-up spec will define the agent-process endpoint that retrieves an agent result.
- This spec prepares repositories, services, configuration, models, and routing only.
- Existing agents should not be changed in this spec.
- Workflow status transition behavior is deferred to the next spec.
- Any decision about `process_agents_status` or analytics/history collections is deferred.
